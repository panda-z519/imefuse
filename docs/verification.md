## 二、微信键盘 WeType

### 格式

- 位置：`~/Library/Application Support/WeType/userDict/v5/<dbid>/`（LevelDB）
- 编码：**key 明文，value 每字节 +6（mod 256）**
- `!v2u!<拼音>`（逗号分隔）= 用户词频表，value 布局：
  `[1]=词长 [3:7]=计数u32 [7:11]=时间u32 … [n-8-词长:n-8]=词面UTF-8`
- 尾部固定 8 字节：`(len-14)&0xFF | FA FA FA | 54 9F 54 9F`（35015 条里 35013 条吻合）

### 写入

向 LevelDB 的 WAL 追加 WriteBatch（自实现 crc32c + LevelDB 掩码），不动 SSTable/MANIFEST。重启后引擎自己 compaction，记录存活。

### 验证

- 导出 2320 条，抽样人工核对无误
- 注入后重启：引擎完成 compaction，记录存活且计数正确
- 行为：见上表三步
- 幂等：同一份导出再导入 → 2320 条全部 `keep`，0 写入

## 三、豆包 DoubaoIme

### 格式

- 位置：`~/Application Support/DoubaoIme/EngineUserDictAccounts/<sha256(uid)>/usr.dat`
- 容器：64B 头 + 140B 统计区 + 2500×u32 索引 + 80000B 记录区（预分配，不增长）
- 记录：`attr(16B: freq/pseudo_time/ptime/flags) + u16 key_len + key + u16 value_len + value`
- key：每音节一个 u16，`code = 36 + 排序音节表下标`
- value：**UTF-16 且整体加密** —— `enc8(c)=rol8(c^0xA5,5)`、`enc16(c)=rol16(c^0x65C9,9)`
  （这就是为什么直接 `strings` 扫不到任何中文）
- 最强证据：解析 → 重新序列化 → 与原文件 **90204 字节逐字节相同**

### 验证

- 写入 1 条 → 重启 → 记录存活 → 打 `cipinhebingyanzheng` 上屏「词频合并验证」
- 批量迁移 1318 条 WeType 词 → 打 `xuyao`/`zhege` 上屏「需要」「这个」
- 容量红线：**2500 条记录 / 80000 字节**，实测 1318 条用掉 59177 字节 —— 再往里塞约 300 条就到顶

## 四、搜狗 Sogou

### 格式（已完全逆出）

- 位置：`~/Library/Application Support/Sogou/InputMethod/SogouPY.users/00000001/sgim_gd_usr.bin`
- 容器：`SGPU` + 0x28 头 + 0x54 目录 + sec0（40000 槽的**有序偏移数组**）+ sec1（arena）
- 记录：`tag u16 / gen u32 / flags / type u8 / hl / head拼音 / bl / wlen / 词UTF-16LE / pylen / trail拼音`
- 拼音：**音节表下标**，表在 `SogouImeKernelResources.bundle/SogouInput/sgim_InputStr.bin`
- **没有词频计数器**：`gen` 是保存代次（同一词敲 3 次只留 1 条、1 个 gen，引擎原地重写）

### 写回：踩了一个坑，最后解决了

写回的文件一开始会被引擎**直接删除**。用「同一文件最小变更 + 启动看存活」二分，定位到唯一被校验的字段：

| 变体 | 结果 |
|---|---|
| 字节完全相同重写 | ✅ 存活 |
| `GEN`(0x28) +1 / `0x30` +1 / `0x2c` +1 / `GENSUM`(0x34) +1 | ✅ 存活 |
| **`NONCE`(0x20) +1** | ❌ 被删 |

取引擎自己两次保存做差：

```
T0: nonce=1455861040  arena_used=1081987  count=33461
T1: nonce=1455861098  arena_used=1082043  count=33463
Δnonce = 58 = Δarena_used(56) + Δcount(2)
nonce - arena_used - count 恒等于 1454745592（文件出生时的 base）
```

所以 **`O_NONCE = base + arena_used + count`**，写回时按增量更新即可（不需要知道 base）：

```python
new_nonce = old_nonce - old_arena_used - old_count + new_arena_used + new_count
```

### 修复后验证

- 追加 1 条 → 文件存活 → 打 `cipinhebingyanzheng` 上屏「词频合并验证」✅
- 批量导入 300 条微信键盘的词 → 全部 ok，33766 条，arena 1096726/1390000
- 打 `canbu` / `xiaoai` 上屏「餐补」「小爱」✅
- 再重启一次仍稳定

## 五、合并语义（按「只合并、不覆盖」实现）

| 策略 | 语义 | 公式 |
|---|---|---|
| **P1（默认）** | 量纲对齐后累加 | `merged = old + round(new × median_old/median_new)` |
| P2 | 直接累加 | `merged = old + new` |
| P3 | 取大 | `merged = max(old, new)` |
| P4 | 加权融合 | `merged = α·old + (1-α)·new_scaled` |

硬规则（不可关闭）：

1. 只增不删 —— 已有词条永不移除
2. 只升不降 —— `merged ≥ old`，否则拒绝该条
3. 不碰无关条目 —— 不参与合并的键一个字节都不重写
4. 幂等 —— 计数相同时判 `keep`；同一 `export_id` 重复导入默认 0 变更
5. 目标不存词频时（搜狗）只做并集，`bump` 一律跳过

## 七、遗留与下一步

1. **豆包容量**：2500 条 / 80KB 是硬上限，实测 1318 条用掉 59177 字节。全量迁移需分批或做词频截断。
2. **搜狗容量**：arena 1390000 字节（已用 1096726）、索引 40000 槽（已用 33768）。到顶需要 compaction，还没做。
3. **云同步**：需要一次真实的「导入后等同步」观察，确认不会被云端覆盖。三家都登录着，这是唯一还没验证的风险点。
4. **搜狗无词频**：只能迁词条不能迁频次，跨到搜狗时 `bump` 一律跳过。
5. **微信键盘 `!dcact!`**：28911 条逐条记录中间有未知字段，目前只读不写；写回只走 `!v2u!`（已验证足够）。
